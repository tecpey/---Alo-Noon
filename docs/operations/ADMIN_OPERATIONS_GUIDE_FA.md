# راهنمای راه‌اندازی و مدیریت عملیات — الو نون

این سند مرجع پیکربندی درگاه پرداخت و سرویس پیامک است — هم از پنل مدیریت، هم از
خط فرمان.

> [!IMPORTANT] **دو مسیر وجود دارد و ترتیبشان مهم است.** پنل مدیریت (`/admin`)
> کار روزمره را انجام می‌دهد، اما برای ورود به آن باید بتوانید پیامک دریافت کنید
> و حسابتان دسترسی مدیریت داشته باشد. هیچ‌کدام از این دو در ابتدا برقرار نیست،
> پس **راه‌اندازی اولیه حتماً از خط فرمان است**. بخش
> [راه‌اندازی اولیه](#بوتاسترپ) این ترتیب را گام‌به‌گام می‌گوید.

هر دستوری که در این راهنما آمده، پیش از انتشار روی PostgreSQL واقعی اجرا و
خروجی‌اش تأیید شده است. صفحه‌های پنل نیز با مرورگر واقعی و API واقعی آزموده
شده‌اند. آنچه اجرا نشده باشد در این سند نیامده.

<a id="پیشنیازها"></a>

## پیش‌نیازها

- دسترسی shell به سروری که API روی آن اجرا می‌شود
- مقدار `DATABASE_URL` تنظیم‌شده
- شناسهٔ tenant (یک UUID). برای پایلوت بابل یک tenant وجود دارد.

همهٔ دستورها از ریشهٔ مخزن اجرا می‌شوند:

```bash
pnpm --filter @alo-noon/api provision <دستور> [--پرچم مقدار]
```

اجرای بدون آرگومان، فهرست دستورهای موجود را نشان می‌دهد.

<a id="مفاهیم-پایه"></a>

## مفاهیم پایه

پیش از اجرای دستورها، سه نکته که رفتار سیستم را توضیح می‌دهند:

**۱. رمز هرگز در پایگاه داده ذخیره نمی‌شود.** آنچه ذخیره می‌شود یک _ارجاع_ است،
مثل `local-encrypted://IDPAY`. خود رمز جای دیگری نگهداری می‌شود و فقط در لحظهٔ
تماس با درگاه باز می‌شود.

**۲. پایگاه داده برای اعتبارنامهٔ پرداخت، `env://` را ممنوع کرده است.** این یک
قید سطح دیتابیس است، نه یک قرارداد نرم. فقط این طرح‌ها مجازند: `vault://`،
`aws-sm://`، `gcp-sm://`، `local-encrypted://`. برای استقراری که مدیر رمز
اختصاصی ندارد، `local-encrypted://` گزینهٔ درست است. برای **پیامک** `env://`
مجاز است.

**۳. یک درگاه تا وقتی «سالم» نشود انتخاب نمی‌شود.** پیکربندی تازه با وضعیت
`UNKNOWN` ساخته می‌شود و انتخاب‌گر فقط `HEALTHY` را می‌پذیرد. این عمدی است: تا
وقتی خودتان تأیید نکرده‌اید درگاه واقعاً کار می‌کند، ترافیک به آن نمی‌رود.

<a id="بوتاسترپ"></a>

## راه‌اندازی اولیه — ترتیب اجباری

پنل مدیریت با همان ورود پیامکی مشتری کار می‌کند و هر صفحه‌اش دسترسی
`payment-provider.configuration.govern` یا
`auth-delivery-provider.configuration.govern` می‌خواهد. نتیجه یک وابستگی دوطرفه
است: برای ورود به پنل پیامک لازم است، و برای پیکربندی پیامک ورود به پنل. تنها
راه شکستن این حلقه، خط فرمان است — و فقط همین یک بار.

**۱. سرویس پیامک را از خط فرمان ثبت کنید.** [گام ۳](#گام-۳) را انجام دهید. تا
اینجا هیچ‌کس نمی‌تواند وارد شود.

**۲. با شمارهٔ خودتان یک بار وارد شوید.** به `/admin/login` بروید، شماره را وارد
کنید و کد را تأیید کنید. ورود موفق می‌شود ولی داشبورد پیام «این حساب اجازهٔ
مدیریت سرویس‌دهنده‌ها را ندارد» می‌دهد — این درست است، حساب هنوز دسترسی ندارد.
همین ورود، حسابِ شما را در پایگاه داده می‌سازد.

**۳. دسترسی مدیریت را به همان شماره بدهید.**

```bash
pnpm --filter @alo-noon/api provision grant-role \
  --tenant <TENANT_UUID> \
  --mobile +989121234567 \
  --role TENANT_ADMIN \
  --reason "اولین اپراتور پیش از سافت‌لانچ"
```

خروجی:

```
Role TENANT_ADMIN granted to +989121234567
Permissions: payment-provider.configuration.govern, ...
```

فهرست نقش‌ها و دسترسی‌هایشان را با `provision list-roles` ببینید (به tenant
نیازی ندارد). نقش‌های موجود:

| نقش                  | برای چه کسی                  |
| -------------------- | ---------------------------- |
| `TENANT_ADMIN`       | همه چیز — برای اولین اپراتور |
| `PROVIDER_GOVERNOR`  | فقط پیکربندی درگاه و پیامک   |
| `OPERATIONS_ANALYST` | فقط دیدن گزارش‌ها و سفارش‌ها |
| `CATALOG_MANAGER`    | مدیریت کاتالوگ و قیمت        |
| `ACCESS_ADMIN`       | فقط دادن و گرفتن دسترسی      |

اگر حساب هنوز ساخته نشده باشد دستور با پیام روشن متوقف می‌شود:
`No identity account for +98...; sign in once with OTP first`. یعنی گام ۲ را رد
کرده‌اید.

**۴. صفحهٔ `/admin` را دوباره باز کنید.** حالا فهرست‌ها و فرم‌ها را می‌بینید و
بقیهٔ کار — از جمله درگاه پرداخت — از خود پنل انجام می‌شود.

برای گرفتن دسترسی از کسی:

```bash
pnpm --filter @alo-noon/api provision revoke-role \
  --tenant <TENANT_UUID> --mobile +989121234567 --role TENANT_ADMIN \
  --reason "پایان همکاری"
```

برای دیدن اینکه چه کسی چه دسترسی‌ای دارد:

```bash
pnpm --filter @alo-noon/api provision list-staff --tenant <TENANT_UUID>
```

هر دو دستور idempotent هستند؛ اجرای دوباره پیام «از قبل دارد» یا «چیزی برای لغو
نیست» می‌دهد و چیزی را خراب نمی‌کند. هر دو در `AuditEvent` ثبت می‌شوند.

<a id="گام-۱"></a>

## گام ۱ — کلید رمزنگاری

یک بار برای هر محیط انجام می‌شود.

```bash
pnpm --filter @alo-noon/api provision generate-encryption-key
```

خروجی یک کلید ۳۲ بایتی base64 (۴۴ کاراکتر) است. آن را در متغیر محیطی
`PAYMENT_SECRET_ENCRYPTION_KEY` سرور قرار دهید.

> [!WARNING] این کلید را در مخزن، تیکت، اسکرین‌شات یا پیام commit نگذارید. اگر
> گم شود، اعتبارنامه‌های رمزشده قابل بازگشایی نیستند و باید از درگاه کلید جدید
> بگیرید. کلید رمزنگاری و مقدارهای رمزشده باید در دو جای جدا نگهداری شوند؛ اگر
> کنار هم باشند، رمزنگاری بی‌اثر است.

<a id="گام-۲"></a>

## گام ۲ — پیکربندی درگاه پرداخت

### ۲-۱. رمز درگاه را رمز کنید

کلید API که از درگاه (مثلاً آی‌دی‌پی) گرفته‌اید را رمز کنید:

```bash
pnpm --filter @alo-noon/api provision encrypt-payment-secret \
  --secret "کلید-واقعی-درگاه" \
  --encryption-key "$PAYMENT_SECRET_ENCRYPTION_KEY"
```

خروجی یک رشتهٔ base64 است. آن را در متغیر محیطی `PAYMENT_SECRET_IDPAY` بگذارید.

قاعدهٔ نام‌گذاری: برای ارجاع `local-encrypted://X`، متغیر محیطی
`PAYMENT_SECRET_X` خوانده می‌شود.

هر بار اجرای این دستور خروجی متفاوتی می‌دهد (بردار اولیهٔ تازه)؛ این درست است و
نشانهٔ خطا نیست.

### ۲-۲. درگاه را ثبت کنید

```bash
pnpm --filter @alo-noon/api provision configure-payment-gateway \
  --tenant "<شناسه-tenant>" \
  --provider IDPAY \
  --environment TEST \
  --credential-reference "local-encrypted://IDPAY" \
  --merchant-reference "<شناسه-پذیرندهٔ-شما>" \
  --reason "راه‌اندازی سافت‌لانچ"
```

درگاه‌های پشتیبانی‌شده: `IDPAY`، `NEXTPAY`، `SHEPA`.

برای محیط واقعی `--environment PRODUCTION` بدهید.

خروجی موفق `configurationId` را چاپ می‌کند — آن را نگه دارید، برای گام بعد لازم
است.

> [!NOTE] **دربارهٔ واحد مبلغ:** نکست‌پی مبلغ را به **تومان** می‌گیرد و آی‌دی‌پی
> و شپا به **ریال**. این تبدیل داخل کد انجام می‌شود و نیازی به کار شما ندارد؛
> اما اولین تراکنش واقعی را حتماً با مبلغ کم بررسی کنید تا از درستی آن مطمئن
> شوید.

### ۲-۳. درگاه را سالم اعلام کنید

تا این لحظه درگاه ثبت شده ولی **استفاده نمی‌شود**. پس از اینکه با یک تراکنش
آزمایشی مطمئن شدید کار می‌کند:

```bash
pnpm --filter @alo-noon/api provision set-payment-gateway-health \
  --tenant "<شناسه-tenant>" \
  --configuration "<configurationId>" \
  --health HEALTHY \
  --reason "تراکنش آزمایشی موفق"
```

اکنون درگاه فعال است.

### ۲-۴. متغیرهای لازم سرور

```bash
PAYMENT_SECRET_ENCRYPTION_KEY=<کلید گام ۱>
PAYMENT_SECRET_IDPAY=<مقدار رمزشدهٔ گام ۲-۱>
PAYMENT_CALLBACK_BASE_URL=https://api.<دامنهٔ-شما>
PAYMENT_RESULT_REDIRECT_URL=https://<اپ-شما>/payments/result
```

بدون `PAYMENT_CALLBACK_BASE_URL` هیچ adapter پرداختی ثبت نمی‌شود. بدون
`PAYMENT_RESULT_REDIRECT_URL` مسیر بازگشت از درگاه ثبت نمی‌شود و مشتری پس از
پرداخت به صفحهٔ خطا می‌رسد.

<a id="گام-۳"></a>

## گام ۳ — پیکربندی پنل پیامک

```bash
pnpm --filter @alo-noon/api provision configure-sms-provider \
  --tenant "<شناسه-tenant>" \
  --provider LIMOSMS \
  --environment TEST \
  --credential-reference "env://AUTH_SMS_LIMOSMS_KEY" \
  --sender "<شمارهٔ-خط-شما>" \
  --template "otp-fa" \
  --reason "راه‌اندازی سافت‌لانچ"
```

سپس کلید پنل پیامک را در متغیر محیطی `AUTH_SMS_LIMOSMS_KEY` قرار دهید.

قاعده: ارجاع `env://AUTH_SMS_X` از متغیر محیطی `AUTH_SMS_X` خوانده می‌شود و باید
با `AUTH_SMS_` شروع شود.

`--sender` باید دقیقاً همان شمارهٔ خطی باشد که در پنل لیمو به شما داده شده است.

### `--template` **متن پیامک نیست**

این یک برچسب است، برای روزی که درگاهی با سرویس «الگو/پترن» اضافه شود؛ لیمو
اس‌ام‌اس چنین سرویسی ندارد و پیام را به‌صورت متن معمولی می‌فرستد. هر مقدار
یادآوری‌کننده‌ای مثل `otp-fa` کافی است.

**متن واقعی پیامک‌ها در پنل، صفحهٔ [متن پیام‌ها](#پیامها) ویرایش می‌شود** — نه
اینجا. این جدایی عمدی است: پیکربندی درگاه پس از ساخت تغییرناپذیر است، و اگر متن
پیام هم داخل آن بود، اصلاح یک غلط املایی به ساختن یک پیکربندی تازه نیاز داشت.

> [!NOTE] **این درگاه کد خطا برنمی‌گرداند.** پاسخش فقط یک `Success` بولی و یک
> جملهٔ فارسی است. به همین دلیل «تلاش دوباره» فقط بر اساس خطای شبکه یا خطای ۵xx
> انجام می‌شود؛ وقتی درگاه صریحاً «نه» بگوید (مثلاً اعتبار کافی نیست) تلاش
> دوباره نمی‌شود، چون تشخیص خطای موقت از دائمی از روی متن ممکن نیست و تکرار،
> اعتبار پنل را روی یک حدس خرج می‌کند. اگر ارسال‌ها یک‌باره `REJECTED` شدند، اول
> موجودی و وضعیت خط را در پنل لیمو بررسی کنید.

> [!IMPORTANT] **پیکربندی پیامک پس از ساخت تغییرناپذیر است.** این را یک trigger
> در پایگاه داده اعمال می‌کند. نام درگاه، شمارهٔ خط، الگو، ارجاع اعتبارنامه و
> وضعیت پیش‌فرض پس از ثبت قابل ویرایش **نیستند** و رکورد هم قابل حذف نیست. پیش
> از اجرا مقادیر را دقیق بررسی کنید. برای خارج‌کردن یک درگاه از مدار، از دستور
> سلامت (پایین) استفاده کنید.

> [!TIP] **کلید API را در چت، تیکت یا کد نگذارید.** پایگاه داده فقط _ارجاع_
> (`env://AUTH_SMS_LIMOSMS_KEY`) را نگه می‌دارد و مقدار واقعی فقط باید در متغیر
> محیطی سرور باشد. اگر کلیدی جایی بیرون از سرور دیده شد، از پنل لیمو یک کلید
> تازه بگیرید و مقدار متغیر محیطی را عوض کنید؛ چون پیکربندی تغییرناپذیر است اما
> _مقدار_ پشت ارجاع هر وقت لازم شد قابل تعویض است.

<a id="پنل"></a>

## پنل مدیریت

پس از [راه‌اندازی اولیه](#بوتاسترپ)، همهٔ کارهای بالا از رابط گرافیکی هم انجام
می‌شوند.

### آدرس‌ها

| صفحه    | مسیر               | کار                                               |
| ------- | ------------------ | ------------------------------------------------- |
| ورود    | `/admin/login`     | دریافت و تأیید کد پیامکی                          |
| داشبورد | `/admin`           | فهرست و مدیریت درگاه‌های پرداخت و سرویس‌های پیامک |
| پیام‌ها | `/admin/messaging` | متن پیامک‌هایی که برای مشتری فرستاده می‌شود       |

### پیکربندی لازم برای پنل

پنل روی `apps/web` اجرا می‌شود و برای تماس با API یک متغیر می‌خواهد:

```
ADMIN_API_BASE_URL=https://<هاست همان tenant>
```

**این مقدار باید هاستِ tenant باشد، نه یک آدرس داخلی.** دلیلش این است که API
تشخیص می‌دهد درخواست به کدام tenant تعلق دارد از روی هاستی که درخواست روی آن
رسیده، و `fetch` در Node اجازهٔ جایگزینی هدر `Host` را نمی‌دهد؛ پس هاستی که API
می‌بیند همان هاستِ داخل این آدرس است. اگر اینجا `http://127.0.0.1:3001` بگذارید،
هیچ tenant پیدا نمی‌شود و پنل شما را مدام به صفحهٔ ورود برمی‌گرداند.

پنل هدر `X-Forwarded-Host` را هم می‌فرستد. اگر `API_TRUST_PROXY_HOPS` را تنظیم
کرده باشید، API آن را ترجیح می‌دهد و یک پنل می‌تواند چند هاستِ tenant را سرویس
دهد. اگر تنظیم نکرده باشید، همان هاستِ `ADMIN_API_BASE_URL` ملاک است.

### آنچه پنل انجام می‌دهد

**درگاه پرداخت** — سه مرحله در بخش «افزودن درگاه جدید»:

1. **ثبت ارجاع کلید** — کد درگاه و ارجاع (مثل `local-encrypted://IDPAY`). خروجی
   یک شناسه است که در مرحلهٔ بعد لازم می‌شود.
2. **ساخت پیکربندی** — شناسهٔ بالا، شناسهٔ پذیرنده، محیط و دلیل. نتیجه غیرفعال و
   با سلامت «نامشخص» ساخته می‌شود.
3. **فعال‌سازی و ثبت سلامت** — روی خود ردیف درگاه. تا هر دو انجام نشود، هیچ
   پرداختی به آن درگاه نمی‌رود.

**سرویس پیامک** — یک فرم در «افزودن سرویس پیامک». این پیکربندی پس از ثبت
تغییرناپذیر است؛ تنها کنترل بعدی، وضعیت سلامت روی همان ردیف است.

### آنچه پنل انجام نمی‌دهد

**هیچ رمزی از پنل عبور نمی‌کند.** فرم‌ها فقط _ارجاع_ می‌گیرند. مقدار واقعی کلید
در محیط اجرا می‌ماند و نه ذخیره می‌شود، نه از پنل قابل خواندن است. برای گذاشتن
مقدارِ رمزشده در محیط، همچنان [گام ۲-۱](#گام-۲) و متغیرهای سرور را لازم دارید.

**دادن و گرفتن دسترسی از صفحهٔ «دسترسی‌ها» انجام می‌شود**، ولی با یک قید سخت:
شما فقط نقشی را می‌توانید بدهید که خودتان همهٔ دسترسی‌هایش را دارید. بدون این
قید، کسی که تنها اختیارش مدیریت دسترسی است می‌توانست خودش را مدیر کل کند. همین
قید هنگام لغو هم برقرار است، وگرنه یک اپراتور محدود می‌توانست همهٔ اپراتورهای
بالادستی را حذف کند و تنها بماند.

**حساب نمی‌تواند دسترسی خودش را لغو کند.** اگر آخرین `TENANT_ADMIN` به هر دلیلی
دسترسی‌اش را از دست بدهد، بازگرداندنش فقط با `provision grant-role` از خط فرمان
سرور ممکن است — پس خط فرمان همچنان راه نجات است، نه راه روزمره.

طرف مقابل باید **یک بار با همان شماره وارد شده باشد**؛ ورود است که حسابش را
می‌سازد و ثابت می‌کند شماره در اختیار خودش است.

فهرست «دسترسی‌ها» فقط حساب‌هایی را نشان می‌دهد که نقش مدیریتی دارند یا
داشته‌اند. مشتری‌ها هم حساب هویتی دارند، و آوردنشان در این صفحه آن را به دفترچهٔ
تلفن مشتری تبدیل می‌کرد.

### وقتی پیام خطا می‌بینید

هر خطا زیر همان فرم و به فارسی نمایش داده می‌شود. چند مورد پرتکرار:

| پیام                                           | معنی                                                                                           |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| این حساب اجازهٔ مدیریت سرویس‌دهنده‌ها را ندارد | دسترسی روی حساب ثبت نشده، یا لغو شده است                                                       |
| برای این درگاه و این نسخه، آداپتوری وجود ندارد | کد درگاه یا نسخهٔ آداپتور با آنچه نصب است نمی‌خواند، یا `PAYMENT_CALLBACK_BASE_URL` تنظیم نشده |
| یک درگاه پیش‌فرض دیگر در همین محیط فعال است    | اول درگاه پیش‌فرض فعلی را غیرفعال کنید                                                         |
| ارجاع env:// باید با AUTH_SMS_ شروع شود        | ارجاع پیامک باید دقیقاً به شکل `env://AUTH_SMS_...` باشد                                       |
| ارجاع کلید معتبر نیست                          | برای پرداخت، `env://` مجاز نیست — به [مفاهیم پایه](#مفاهیم-پایه) برگردید                       |

اگر کدی دیدید که ترجمه نشده، خود کد داخل پرانتز نمایش داده می‌شود؛ همان را در
بخش [عیب‌یابی](#عیبیابی) یا در لاگ API جست‌وجو کنید.

<a id="تسویه"></a>

## چرخهٔ پرداخت و تسویه

پس از بازگشت مشتری از درگاه، سیستم **خودش** با درگاه تماس سرور-به-سرور می‌گیرد و
می‌پرسد آیا پرداخت واقعاً انجام شده و **دقیقاً چقدر**. تا وقتی پاسخ درگاه با
مبلغ سفارش برابر نباشد، هیچ پولی ثبت نمی‌شود.

### چه چیزی خودکار است

| رخداد                                  | نتیجه                                                        |
| -------------------------------------- | ------------------------------------------------------------ |
| درگاه پرداخت را با مبلغ درست تأیید کند | پرداخت `CAPTURED`، سند دوطرفه در دفتر کل، سفارش `PAID`       |
| درگاه بگوید پرداخت ناموفق بوده         | تلاش پرداخت `REJECTED`، هیچ سندی ثبت نمی‌شود                 |
| درگاه هنوز پاسخ قطعی ندهد              | چیزی تغییر نمی‌کند؛ جاروی خودکار هر دقیقه دوباره تلاش می‌کند |
| **مبلغ تأییدشده با مبلغ سفارش نخواند** | **قرنطینه** — نه ثبت می‌شود، نه دور انداخته می‌شود           |

### قرنطینه یعنی چه، و چه باید کرد

قرنطینه وقتی رخ می‌دهد که درگاه «بله» می‌گوید ولی چیزی جور در نمی‌آید: مبلغ کمتر
یا بیشتر از سفارش، یا شناسهٔ تراکنشی متفاوت. این عمداً خودکار حل نمی‌شود، چون یا
حمله است یا اشکال — و هر دو باید دیده شوند.

این‌ها را در پایگاه داده با این پرس‌وجو پیدا می‌کنید:

```sql
SELECT r."id", r."externalEventId", a."metadata"->>'reasonCode' AS reason, r."receivedAt"
FROM "PaymentCallbackReceipt" r
JOIN "AuditEvent" a ON a."entityId" = r."id"
  AND a."action" = 'payment.callback_settlement_decided'
WHERE r."tenantId" = '<TENANT_UUID>' AND r."processingStatus" = 'REJECTED'
ORDER BY r."receivedAt" DESC;
```

کدهای `reasonCode` که نیاز به بررسی انسانی دارند:

| کد                               | معنی                                            |
| -------------------------------- | ----------------------------------------------- |
| `SETTLEMENT_AMOUNT_MISMATCH`     | درگاه مبلغی غیر از مبلغ سفارش را تأیید کرده     |
| `SETTLEMENT_AMOUNT_NOT_REPORTED` | درگاه تأیید کرده ولی مبلغ قابل خواندنی نفرستاده |
| `SETTLEMENT_REFERENCE_MISMATCH`  | تأییدیه برای تراکنش دیگری است                   |
| `SETTLEMENT_ATTEMPT_NOT_FOUND`   | بازگشتی رسیده که به هیچ تلاش پرداختی وصل نیست   |

### پرداخت‌هایی که هنوز تسویه نشده‌اند

اگر درگاه در لحظهٔ بازگشت مشتری در دسترس نباشد، رسید بدون نتیجه می‌ماند و جاروی
خودکار (هر ۶۰ ثانیه) دوباره تلاش می‌کند. برای دیدن آنچه در صف مانده:

```sql
SELECT count(*) FROM "PaymentCallbackReceipt"
WHERE "tenantId" = '<TENANT_UUID>' AND "processingStatus" = 'RECEIVED';
```

اگر این عدد بالا و ثابت ماند، یعنی تماس با درگاه برقرار نمی‌شود — لاگ API را با
`Payment settlement sweep failed` یا
`Payment callbacks still awaiting settlement` جست‌وجو کنید.

> [!IMPORTANT] **نکتهٔ نکست‌پی:** نکست‌پی به تومان کار می‌کند. مبلغی که مضرب ۱۰
> ریال نباشد اصلاً قابل تأیید نیست و سیستم به‌جای گرد کردن، تسویه را رد می‌کند.
> اگر از نکست‌پی استفاده می‌کنید، قیمت‌ها را طوری تنظیم کنید که جمع سفارش همیشه
> مضرب ۱۰ ریال باشد.

<a id="کاتالوگ"></a>

## کاتالوگ و قیمت‌گذاری

دو صفحهٔ جدا در پنل، چون دو تصمیم جدا هستند:

- **کاتالوگ** می‌گوید **نان چیست** — نام، طبقه‌بندی، مواد اولیه. یک بار برای کل
  سامانه تعریف می‌شود.
- **قیمت‌گذاری** می‌گوید **کدام شعبه آن را به چه قیمتی می‌فروشد**. یک گونه در دو
  شعبه، دو عرضهٔ جدا با دو قیمت است.

### ترتیب کار

۱. **دسته** بسازید (یک بار، مثلاً «نان سنتی»).

۲. **محصول** بسازید. `slug` در نشانی اینترنتی محصول ظاهر می‌شود و بعداً عوض
نمی‌شود.

۳. **گونه** بسازید. این همان چیزی است که مشتری سفارش می‌دهد. **طبقه‌بندی پس از
ساخت قابل تغییر نیست** — زمان‌بندی تولید و تحویل بر پایهٔ آن انجام می‌شود و
تغییرش کارِ در جریان را دوباره برنامه‌ریزی می‌کند.

۴. در صفحهٔ **قیمت‌گذاری**، گونه را به یک شعبه با یک قیمت اضافه کنید.

۵. محصول و گونه را **فعال** کنید، سپس عرضه را **منتشر** کنید.

هر سه — محصول، گونه، عرضه — پیش‌نویس ساخته می‌شوند. این عمدی است: چیزی که تازه
نام گرفته نباید پیش از قیمت‌گذاری قابل فروش باشد.

### قاعده‌هایی که سامانه اجرا می‌کند

| کار                                        | نتیجه                                                  |
| ------------------------------------------ | ------------------------------------------------------ |
| انتشار عرضه وقتی گونه یا محصول فعال نیست   | رد می‌شود؛ اول آن‌ها را فعال کنید                      |
| بازنشسته کردن گونه‌ای که شعبه‌ای می‌فروشد  | رد می‌شود؛ اول عرضه‌ها را متوقف کنید                   |
| افزودن همان گونه به همان شعبه برای بار دوم | رد می‌شود؛ هر گونه در هر شعبه فقط یک قیمت دارد         |
| بازگرداندن چیزی از «بازنشسته»              | ممکن نیست؛ بازنشسته پایانی است و باید ردیف تازه بسازید |
| قیمت صفر یا منفی                           | رد می‌شود                                              |
| موجودی بدون روشن بودن شمارش موجودی         | رد می‌شود؛ این دو همیشه با هم تنظیم می‌شوند            |

### تغییر قیمت

**تغییر قیمت روی سفارش‌های ثبت‌شده اثری ندارد.** هر سفارش قیمت، نام و SKU لحظهٔ
خودش را در سطرهایش نگه می‌دارد؛ قیمتی که امروز بعدازظهر بالا می‌برید نمی‌تواند
سفارش صبح را عوض کند.

قیمت قبلی در `AuditEvent` ثبت می‌شود. برای پیدا کردن تاریخچهٔ قیمت یک عرضه:

```sql
SELECT a."occurredAt", a."actorId", e.payload->>'fromPrice' AS from_price,
       e.payload->>'toPrice' AS to_price, e.payload->>'reason' AS reason
FROM "AuditEvent" a
JOIN "DomainEventOutbox" e
  ON e."correlationId" = a."correlationId" AND e."aggregateId" = a."entityId"
WHERE a."entityId" = '<offeringId>'
  AND a.action = 'catalog.offering_updated'
ORDER BY a."occurredAt" DESC;
```

### موجودی

شمارش موجودی فقط برای کالای بسته‌بندی‌شده معنا دارد. نان تازه‌پخت با **ظرفیت
روزانه** کنترل می‌شود، نه با شمارش واحد — چون هنوز پخته نشده که شمرده شود.

### دسترسی لازم

همهٔ این صفحه‌ها `admin.catalog.manage` می‌خواهند؛ نقش `CATALOG_MANAGER` یا
`TENANT_ADMIN`. دسترسی هنگام هر نوشتن، دوباره از ردیف‌های زندهٔ پایگاه داده
خوانده می‌شود، پس لغو دسترسی بلافاصله اثر می‌کند و منتظر انقضای نشست نمی‌ماند.

<a id="پیامها"></a>

## متن پیام‌ها

صفحهٔ `/admin/messaging`. هر پیامکی که سیستم برای مشتری می‌فرستد اینجا فهرست
می‌شود و متنش قابل ویرایش است. دسترسی لازم:
`notification-provider.configuration.govern` (نقش‌های `PROVIDER_GOVERNOR` و
`TENANT_ADMIN`).

پیام‌های موجود:

| پیام              | کِی فرستاده می‌شود               |
| ----------------- | -------------------------------- |
| کد ورود یکبارمصرف | هنگام ورود مشتری یا اپراتور      |
| پذیرش سفارش       | وقتی نانوایی سفارش را می‌پذیرد   |
| رد سفارش          | وقتی نانوایی نمی‌تواند انجام دهد |
| آماده شدن سفارش   | وقتی پخت تمام شده                |
| خروج برای تحویل   | وقتی سفارش تحویل پیک می‌شود      |
| تحویل سفارش       | وقتی به دست مشتری رسیده          |
| لغو سفارش         | وقتی سفارش لغو می‌شود            |

### ارسال چطور انجام می‌شود

پیام‌ها همان لحظه‌ای که اپراتور دکمه را می‌زند فرستاده نمی‌شوند؛ رویداد سفارش
ثبت می‌شود و یک فرآیند پس‌زمینه هر ۱۵ ثانیه آن را برمی‌دارد و پیامک می‌کند. این
عمدی است: اگر ارسال داخل همان تراکنش بود، کندی یا قطعی سرویس پیامک یا مرحلهٔ
سفارش را شکست می‌داد — در حالی که نانوایی نان را گذاشته در کیسه — یا خطا بلعیده
می‌شد و هیچ‌وقت دوباره تلاش نمی‌شد.

اگر ارسال شکست بخورد، تا ۵ بار دوباره تلاش می‌شود و بعد کنار گذاشته می‌شود تا صف
پشت سرش را نبندد. **هر پیام برای هر مرحلهٔ هر سفارش فقط یک بار فرستاده می‌شود**،
حتی اگر فرآیند وسط کار قطع شود.

### متغیرها

جای مقدارهای واقعی با آکولاد مشخص می‌شود؛ مثلاً `{orderCode}` هنگام ارسال با کد
واقعی سفارش عوض می‌شود. **هر پیام فقط متغیرهای خودش را می‌پذیرد** و فهرست مجازها
زیر همان کادر نوشته شده است.

اگر متغیری بنویسید که آن پیام ندارد، ذخیره نمی‌شود و پنل می‌گوید کدام کلمه اشکال
دارد. دلیلش ساده است: چیزی که سیستم نتواند جایگزین کند، عیناً — با همان آکولادها
— برای مشتری فرستاده می‌شد.

بعضی متغیرها **اجباری** هستند. مثلاً پیام کد ورود بدون `{code}` ذخیره نمی‌شود،
چون پیامی که کد ندارد به درد نمی‌خورد.

### کد سفارش

`{orderCode}` یک کد هشت‌کاراکتری مثل `CGBM9XX5` است — کوتاه، بدون حرف و رقمی که
با هم اشتباه شوند (نه `O` در کنار `0`، نه `I` یا `L` در کنار `1`)، و قابل خواندن
پشت تلفن. همین کد است که مشتری برای پیگیری به شما می‌گوید و در صفحهٔ سفارش‌ها
جست‌وجو می‌شود.

### هزینه

زیر هر متن نوشته شده چند پیامک حساب می‌شود. متن فارسی با UCS-2 فرستاده می‌شود:
تا ۷۰ کاراکتر یک پیامک، و از ۷۱ به بعد هر ۶۷ کاراکتر یک پیامک. یعنی یک جملهٔ
تعارف اضافه می‌تواند صورتحساب پیامک را دو برابر کند — عدد زیر کادر همان هزینهٔ
واقعی است.

### دو نکته

**پیام کد ورود خاموش نمی‌شود.** پنل و پایگاه داده هر دو جلویش را می‌گیرند: اگر
خاموش شود هیچ‌کس نمی‌تواند وارد شود، از جمله همان کسی که باید دوباره روشنش کند.

**tenant‌ی که این صفحه را باز نکرده، بی‌پیام نیست.** تا وقتی متنی ذخیره نشود،
متن پیش‌فرض سیستم فرستاده می‌شود و همان هم در این صفحه با برچسب «پیش‌فرض» دیده
می‌شود. متن پیش‌فرض هر پیام، زیر کادر ویرایش نوشته شده تا بشود به آن برگشت.

<a id="مدیریت-روزمره"></a>

## مدیریت روزمره

### دیدن پیکربندی‌های پیامک

```bash
pnpm --filter @alo-noon/api provision list-sms-providers --tenant "<شناسه-tenant>"
```

خروجی نمونه:

```
4419e719-...  LIMOSMS  TEST  enabled=true  default=true  health=HEALTHY
```

### خارج‌کردن یک درگاه پیامک از مدار

هنگام قطعی سرویس پنل پیامک:

```bash
pnpm --filter @alo-noon/api provision set-sms-provider-health \
  --tenant "<شناسه-tenant>" \
  --configuration "<شناسهٔ-پیکربندی>" \
  --health UNHEALTHY \
  --reason "قطعی سرویس ارائه‌دهنده"
```

و پس از رفع مشکل، بازگرداندن آن (که شمارندهٔ خطا و مدار قطع‌شده را هم صفر
می‌کند):

```bash
pnpm --filter @alo-noon/api provision set-sms-provider-health \
  --tenant "<شناسه-tenant>" \
  --configuration "<شناسهٔ-پیکربندی>" \
  --health HEALTHY \
  --reason "سرویس بازگشت"
```

### خارج‌کردن درگاه پرداخت از مدار

همان الگو با `set-payment-gateway-health` و مقدار `UNHEALTHY`.

### ردیابی تغییرات

هر تغییر پیکربندی یک رکورد audit با دلیل، عامل و زمان ثبت می‌کند. برای مرور:

```sql
SELECT "occurredAt", action, summary, metadata
FROM "AuditEvent"
WHERE "entityType" IN (
  'auth_delivery_provider_configuration',
  'payment_provider_configuration'
)
ORDER BY "occurredAt" DESC;
```

## عیب‌یابی

| پیام خطا                                              | معنا و راه‌حل                                                                                                                                            |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AUTH_DELIVERY_CONFIGURATION_CONFLICT`                | همین درگاه با مقادیر متفاوت قبلاً ثبت شده. چون پیکربندی تغییرناپذیر است، یا دقیقاً همان مقادیر قبلی را بدهید، یا با `--adapter-version` متفاوت ثبت کنید. |
| `AUTH_DELIVERY_DEFAULT_ALREADY_EXISTS`                | برای این محیط از قبل یک درگاه پیش‌فرض هست. درگاه جدید را با `--default false` ثبت کنید.                                                                  |
| `AUTH_DELIVERY_ENV_CREDENTIAL_REFERENCE_UNRESOLVABLE` | ارجاع `env://` باید با `AUTH_SMS_` شروع شود، وگرنه هنگام ارسال قابل بازیابی نیست.                                                                        |
| `IDEMPOTENCY_KEY_CONFLICT`                            | همان دستور را با `--reason` متفاوت اجرا کرده‌اید. دلیل بخشی از هویت عملیات است؛ برای اجرای مجدد، **همان دلیل قبلی** را بدهید.                            |
| `PAYMENT_PROVIDER_ADAPTER_UNAVAILABLE`                | نام درگاه پشتیبانی نمی‌شود. فقط `IDPAY`، `NEXTPAY`، `SHEPA`.                                                                                             |
| `PAYMENT_SECRET_KEY_INVALID`                          | کلید رمزنگاری ۳۲ بایت base64 نیست. با `generate-encryption-key` بسازید.                                                                                  |
| `PAYMENT_SECRET_AUTHENTICATION_FAILED`                | مقدار رمزشده با این کلید باز نمی‌شود — یا کلید عوض شده یا مقدار دستکاری/کوتاه شده.                                                                       |
| `PAYMENT_PROVIDER_CREDENTIAL_UNAVAILABLE`             | متغیر محیطی مقدار رمزشده تنظیم نشده، یا `PAYMENT_SECRET_ENCRYPTION_KEY` روی سرور نیست.                                                                   |

### درخواست OTP خطای ۵۰۳ می‌دهد

ترتیب بررسی: (۱) آیا پیکربندی پیامک ثبت شده؟ با `list-sms-providers` ببینید. (۲)
آیا `enabled=true` و `default=true` و `health=HEALTHY` است؟ (۳) آیا adapter آن
درگاه نوشته شده؟ امروز تنها `LIMOSMS` adapter دارد؛ هر درگاه دیگری تا نوشته‌شدن
adapter، ۵۰۳ می‌دهد. (۴) آیا `AUTH_SMS_LIMOSMS_KEY` روی سرور تنظیم است؟ پایگاه
داده فقط ارجاع (`env://AUTH_SMS_LIMOSMS_KEY`) را نگه می‌دارد، نه مقدار را.

### مشتری پس از پرداخت به صفحهٔ خطا می‌رسد

`PAYMENT_RESULT_REDIRECT_URL` تنظیم نشده است. بدون آن، مسیر دریافت بازگشت از
درگاه اصلاً ثبت نمی‌شود.

<a id="آزمایش"></a>

## آزمایش راه‌اندازی بدون پیامک واقعی

پیش از اینکه اولین مشتری واقعی وارد شود، باید مطمئن شوید کل زنجیره کار می‌کند.
مشکل این است که ورود به سیستم پیامک می‌خواهد و آزمایش با شمارهٔ واقعی یعنی
فرستادن پیامک واقعی و خرج‌کردن اعتبار — آزمایشی که باید روی مشتری واقعی انجام
شود، آزمایشی است که هیچ‌کس انجام نمی‌دهد.

برای همین مقصد ارسال پیامک قابل تغییر است:

```bash
AUTH_SMS_LIMOSMS_ENDPOINT=https://<نشانی-سندباکس>/api/sendsms
```

اگر تنظیم نشود، درگاه واقعی لیمو استفاده می‌شود — که همان چیزی است که محیط واقعی
می‌خواهد. **این متغیر را در محیط واقعی تنظیم نکنید.**

### همین کار برای پرداخت

پرداخت هم دقیقاً همین مسئله را دارد، با این تفاوت که زرین‌پال **sandbox رسمی
دارد**. پس ترتیب درست این است:

۱. **اول sandbox خود زرین‌پال.** هیچ چیز تنظیم نکنید؛ هر پیکربندی با
`environment=TEST` خودبه‌خود به `sandbox.zarinpal.com` می‌رود و پیکربندی
`PRODUCTION` به درگاه واقعی. پول واقعی جابه‌جا نمی‌شود.

۲. **اگر شبکه‌تان به sandbox نمی‌رسد** (رانرِ CI بسته، پروکسی شرکتی)، یک ایستگاه
محلی که همان قرارداد v4 را می‌گوید اجرا کنید:

```bash
pnpm --filter @alo-noon/api exec tsx scripts/zarinpal-sandbox.ts
# سپس روی سرور API:
PAYMENT_ZARINPAL_ENDPOINT=http://127.0.0.1:4180
```

این ایستگاه authority می‌سازد، پرداخت‌نشده را با `-51` رد می‌کند، مبلغ ناهمخوان
را با `-50` رد می‌کند، و وریفای دوم را `101` جواب می‌دهد — یعنی همان پنج رفتاری
که adapter به آن‌ها تکیه دارد.

> [!WARNING] `PAYMENT_ZARINPAL_ENDPOINT` را در محیط واقعی تنظیم نکنید. با تنظیم
> آن، پرداخت‌های واقعی به جای درگاه به آن نشانی می‌روند.

**هیچ‌کدام از این دو جای آزمون واقعی را نمی‌گیرد.** اولین تراکنش روی درگاه واقعی
باید با مبلغ کم انجام شود و مبلغ کسرشده از کارت با مبلغ سفارش مقابله شود — واحد
مبلغ تنها چیزی است که اشتباهش ده برابر خرج می‌گذارد.

### دو دستور آزمایشی

```bash
# یک tenant کامل و قابل سفارش‌گرفتن می‌سازد: شهر، ناحیه، نانوایی، شعبه،
# محصول، ظرفیت امروز، تعرفهٔ ارسال، دفتر حساب، اپراتور و پیک.
pnpm --filter @alo-noon/api exec tsx scripts/bootstrap-launch.ts

# یک سفارش واقعی را از ورود مشتری تا دم در می‌راند و هر مرحله را می‌سنجد.
pnpm --filter @alo-noon/api exec tsx scripts/launch-drive.ts
```

دستور دوم همان چیزی را می‌فرستد که سه اپ می‌فرستند — روی HTTP، با همان کوکی‌ها —
پس چیزهایی را می‌آزماید که تست‌های واحد نمی‌توانند: تشخیص tenant از روی دامنه،
ثبت مسیرها، و فرآیندهای پس‌زمینه.

در پایان یا `ALL CHECKS PASSED` می‌بینید یا دقیقاً می‌گوید کدام مرحله شکست خورد.

<a id="چکلیست"></a>

## چک‌لیست سافت‌لانچ

پیش از باز کردن سرویس روی کاربر واقعی:

- [ ] `PAYMENT_SECRET_ENCRYPTION_KEY` ساخته و جدا از مقادیر رمزشده نگهداری شده
- [ ] درگاه پرداخت ثبت شده و پس از تراکنش آزمایشی `HEALTHY` شده
- [ ] `PAYMENT_CALLBACK_BASE_URL` و `PAYMENT_RESULT_REDIRECT_URL` تنظیم شده‌اند
- [ ] یک پرداخت واقعی با مبلغ کم انجام شده و **سفارش آن به وضعیت پرداخت‌شده
      رسیده است** — نه فقط بازگشت مشتری، بلکه تسویهٔ کامل
- [ ] پس از آن پرداخت آزمایشی، جدول `FinancialTransaction` یک سند متوازن دارد
- [ ] هیچ رسید قرنطینه‌شده‌ای در صف نمانده
- [ ] پیکربندی پیامک ثبت شده
- [ ] **`API_TRUST_PROXY_HOPS` تنظیم شده** — اگر پشت لودبالانسر هستید و این را
      تنظیم نکنید، محدودیت نرخ و کنترل سوءاستفادهٔ OTP برای همهٔ کاربران در یک
      سطل مشترک می‌افتد. سرور در حالت production بدون این مقدار بالا نمی‌آید.
- [ ] `AUTH_OTP_PEPPER`، `AUTH_SESSION_PEPPER`، `AUTH_ABUSE_PEPPER` هر سه مقدار
      مستقل دارند
- [ ] سقف روزانهٔ پیامک با حجم پیش‌بینی‌شده و بودجه هم‌خوان است
- [ ] `ADMIN_API_BASE_URL` روی هاستِ همان tenant تنظیم شده، نه یک آدرس داخلی
- [ ] دست‌کم یک اپراتور دسترسی مدیریت گرفته و ورودش به `/admin` آزموده شده
- [ ] دسترسی مدیریت افرادی که دیگر لازمش ندارند لغو شده است

<a id="روادمپ"></a>

## نقشهٔ آینده — آنچه هنوز ساخته نشده

این بخش عمداً از بخش‌های بالا جداست. **هیچ‌کدام از موارد زیر امروز وجود ندارند**
و نباید روی آن‌ها حساب کنید.

فهرست کامل، با قراردادهای تأییدشدهٔ سرویس‌دهنده‌ها و ترتیب پیشنهادی ساخت، در
[سرویس‌های بیرونی و لجستیک](../product/EXTERNAL_INTEGRATIONS_AND_LOGISTICS_ROADMAP.md)
است. خلاصه‌اش:

### درگاه پرداخت — با درگاه واقعی هنوز آزموده نشده

چهار adapter ساخته شده‌اند: `ZARINPAL`، `IDPAY`، `NEXTPAY` و `SHEPA`. مسیر کامل
`initialize → بازگشت مشتری → callback → verify → capture` روی یک درگاه که دقیقاً
قرارداد v4 زرین‌پال را می‌گوید اجرا و آزموده شده — ولی **هنوز روی خود درگاه
زرین‌پال (چه sandbox چه واقعی) اجرا نشده**. زیبال هنوز adapter ندارد.

### پیامک — ارسال واقعی انجام نشده

adapter لیمو ساخته و ثبت شده و با سندباکس محلی آزموده شده، ولی یک پیامک واقعی
هرگز فرستاده نشده.

### مسیریابی، کرایهٔ مبتنی بر فاصله، و سفر چندمقصده — ساخته نشده

فاصلهٔ واقعی محاسبه نمی‌شود، پس کرایه فقط `FLAT` است. پیک هر سفارش را جدا
می‌برد؛ دسته‌بندی چند سفارش هم‌مسیر در یک سفر وجود ندارد.

### گزارش‌های لجستیک — ساخته نشده

هزینهٔ تحویل به‌ازای سفارش، چگالی دسته، و نرخ تحویل‌نشده محاسبه نمی‌شوند.
