# مسیر خرید در اپ موبایل — طراحی بر پایهٔ شواهد

> این سند می‌گوید مسیر خرید **چه باید باشد** و **چرا**، و هر «چرا» را به یک
> پژوهش منتشرشده گره می‌زند. شمارش گام‌ها از خواندن کد واقعی `App.tsx` آمده، نه
> از تخمین.

## پنج مدل علمی که این مسیر را شکل می‌دهند

| مدل                                                  | یافته                                                                                                                                               | نتیجه برای ما                                                 |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **پژوهش سبد خرید Baymard**                           | نرخ رهاکردن سبد **۷۰٫۲۲٪** (میانگین ۵۰ مطالعه). علت‌ها: هزینهٔ غیرمنتظره **۳۹٪**، تحویل کند **۲۱٪**، اجبار به ساخت حساب **۱۹٪**، بی‌اعتمادی **۱۹٪** | هزینه و زمان تحویل را **زود** نشان بده؛ حساب را **دیر** بخواه |
| **Baymard — فیلدهای فرم**                            | در بیشتر checkoutها می‌شود **۲۰ تا ۶۰٪** فیلدها را حذف کرد؛ تایپ روی موبایل به‌مراتب سخت‌تر است                                                     | هر فیلد باید جانش را ثابت کند                                 |
| **قانون هوور (Hoober)**                              | از ۱٬۳۳۳ مشاهدهٔ واقعی: **۴۹٪** تک‌دستی، **۷۵٪** تعامل‌ها با شست                                                                                    | کنش اصلی در **یک‌سوم پایینِ** صفحه                            |
| **اثر شیب‌هدف** (Kivetz, Urminsky & Zheng، JMR ۲۰۰۶) | هرچه به هدف نزدیک‌تر، تلاش بیشتر؛ حتی **پیشرفت ساختگی** سرعت رسیدن را زیاد می‌کند                                                                   | نشانگر پیشرفت واقعی در checkout                               |
| **NN/g — سالمندان**                                  | ۶۵+ ‏**۴۳٪** کندتر؛ بعد از اولین شکست **~۲ برابر** بیشتر رها می‌کنند                                                                                | مسیر اصلی باید بار اول کار کند؛ بن‌بست ممنوع                  |

## ۱. مشکل ساختاری — که اصلاح شد

اپ روی **فیلد شمارهٔ موبایل** باز می‌شد. ترتیب واقعی کد این بود:

```
boot → phone → otp → location (شهر + GPS + بررسی سرویس‌دهی) → catalog
```

یعنی **پنج دروازه پیش از دیدن یک قرص نان یا یک قیمت**:

| #   | دروازه          | اگر رد کند          |
| --- | --------------- | ------------------- |
| ۱   | شمارهٔ موبایل   | جلو نمی‌رود         |
| ۲   | کد پیامکی       | جلو نمی‌رود         |
| ۳   | انتخاب شهر      | جلو نمی‌رود         |
| ۴   | **اجازهٔ GPS**  | **بن‌بست کامل**     |
| ۵   | بررسی سرویس‌دهی | پیام خطا، همان صفحه |

**۱۰ لمس + ۲ فیلد تایپی + ۱ دیالوگ سیستمی** تا ثبت سفارش، و نان در لمس ششم ظاهر
می‌شد.

این دقیقاً وارونهٔ شواهد است. سه‌تا از چهار علت اصلی رهاکردن سبد — هزینهٔ
غیرمنتظره، اجبار به حساب، بی‌اعتمادی — چیزهایی‌اند که مشتری فقط با **نگاه‌کردن
به مغازه** می‌تواند قضاوتشان کند. از غریبه‌ای که هنوز نمی‌داند اینجا چه
می‌فروشند، شمارهٔ موبایل خواستن، ترتیب تصمیم‌گیری برای خرید نان را وارونه
می‌کند.

و این دروازه **مال ما بود، نه مال API**: در قرارداد، `operationalZoneId` روی
کوئری کاتالوگ **اختیاری** است، `listActiveCities` عمومی است، و وب‌سایت از اول
قفسه‌هایش را به بازدیدکنندهٔ ناشناس نشان می‌داده.

### آنچه الان هست

```
boot → catalog (ناشناس، بدون GPS)
          ↓ اولین «افزودن»
       phone → otp → location → catalog (با همان نان در سبد)
```

هویت دقیقاً در لحظه‌ای خواسته می‌شود که **واقعاً لازم است** و **قابل توضیح
است**: مشتری می‌داند برای چه وارد می‌شود.

**یک باگ هم همین‌جا بسته شد:** پیش از این، `addProduct` وقتی زون نداشت بی‌صدا
`return` می‌کرد — یعنی دکمهٔ «افزودن» روی قفسهٔ پر از نان، کنترلی بود که زنده به
نظر می‌رسید و هیچ کاری نمی‌کرد. دکمهٔ مرده از دکمهٔ قفل بدتر است: به مشتری یاد
می‌دهد اپ خراب است، نه اینکه چیزی لازم است.

## ۲. مسیر هدف — کامل

### الف) مشتری ناشناس، بار اول

| گام         | صفحه     | چرا این‌طور                         |
| ----------- | -------- | ----------------------------------- |
| باز کردن اپ | **قفسه** | Baymard: قیمت و جنس پیش از هر تعهدی |
| «+» روی نان | قفسه     | یک لمس، در ناحیهٔ شست               |
| شماره + کد  | ورود     | تنها جایی که هویت لازم است          |
| نشانی       | موقعیت   | **با راه جایگزین اگر GPS رد شد**    |
| پرداخت      | سبد      | مبلغ کامل پیش از تأیید              |

### ب) مشتری برگشتی — هدف: **دو لمس**

این حالت غالب کسب‌وکار نان است. نان هفتهٔ بعد همان نان هفتهٔ پیش است.

```
باز کردن اپ → کارت «همان سفارش قبلی» → پرداخت
```

اثر شیب‌هدف می‌گوید هرچه هدف نزدیک‌تر دیده شود تلاش بیشتر می‌شود؛ سفارش تکراری،
هدفی است که از همان ثانیهٔ اول در دسترس است.

### چرا #۳ بحرانی است

صفحهٔ موقعیت **هیچ دکمهٔ رد کردن ندارد**. اگر مشتری اجازهٔ GPS ندهد — که
سالمندان از روی احتیاط زیاد انجامش می‌دهند — مسیر تمام می‌شود. وب این را حل کرده
(جست‌وجوی نشانی از نشان)؛ موبایل هنوز نه.

### #۳ چطور حل شد

صفحهٔ موقعیت حالا **سه راه** دارد، نه یکی:

۱. **نشانی‌های ذخیره‌شده** — بالاتر از همه و پیش از آنکه چیزی پرسیده شود.
مختصاتش هنگام ذخیره تأیید شده، پس نه پرامپتی در کار است نه تایپی نه سرویس
نقشه‌ای. برای مشتری برگشتی، همین یک لمس کل صفحه است.

۲. **موقعیت ماهواره‌ای** — سریع‌ترین وقتی کار کند.

۳. **نوشتن نشانی** — بسته می‌ماند تا خواسته شود (یک صفحه، یک پرسش)، و **خودش باز
می‌شود** لحظه‌ای که پرامپت رد شود. پیام خطا هم دیگر بن‌بست نیست، راه را نشان
می‌دهد: «اشکالی ندارد — نشانی‌تان را بنویسید».

اگر فروشگاه اصلاً سرویس نقشه نداشته باشد، جعبهٔ جست‌وجو **نمایش داده نمی‌شود**؛
جعبه‌ای که نمی‌تواند جست‌وجو کند از نبودش بدتر است. این تمایز
(`available: false` در برابر `candidates: []`) آزمون دارد.

### چرا #۵ مهم است

هزینهٔ غیرمنتظره **بزرگ‌ترین علت قابل‌اصلاح** رهاکردن سبد است (۳۹٪). الان کرایه
فقط بعد از «دریافت قیمت نهایی» دیده می‌شود — یعنی بعد از ورود، نشانی و انتخاب
بازهٔ تحویل. یک برآورد («کرایه از ۵٬۰۰۰ تومان») روی خودِ قفسه، این را جلو
می‌آورد.

## ۴. آنچه از قبل درست بود

- `touch-targets.test.ts` کفِ اندازهٔ لمسی را روی کد تضمین می‌کند — کاری که خیلی
  از تیم‌ها نمی‌کنند.
- ورود بدون رمز عبور (فقط OTP) — یک فیلد کمتر، و رمزی که فراموش شود وجود ندارد.
- «در اولین فرصت» گزینهٔ پیش‌فرض بازهٔ تحویل است؛ پیش‌فرضِ درست یعنی یک تصمیم
  کمتر.
- کیف پول، پرداخت را به یک لمس می‌رساند.

---

## آنچه این سند ادعا نمی‌کند

مسیر روی **دستگاه واقعی** اجرا و زمان‌گیری نشده؛ شمارش گام‌ها از کد است. و هیچ
کاربر واقعی این مسیر را تست نکرده. Baymard و NN/g می‌گویند چه چیزی برای هزاران
نفر کار کرده — نمی‌گویند مادربزرگی در بابل با این صفحه چه می‌کند. پنج نفر،
بیشترِ آنچه می‌ماند را پیدا می‌کنند.
